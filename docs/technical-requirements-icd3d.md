# نیازمندی‌های فنی ICD 3D (ثاخت)
نسخه هماهنگ‌شده با `sitemap.md` (v1.1) — هلدینگ ساخت‌وساز/املاک پذیرفته‌شده در بورس تهران، با پروژه‌ها، شرکت‌های زیرمجموعه، فروش/پیش‌فروش، دیده‌بان سهامداران، رسانه، و حساب کاربری. زبان اصلی فارسی/راست‌چین، زبان دوم انگلیسی. معماری پایه: **وردپرس برای محتوا و اکثر قالب‌ها + لایه API روی PHP + ماژول‌های React سه‌بعدی روی چند قالب مشخص** (نه فقط هوم‌پیج — sitemap در ۵ صفحه پرچم `3D` گذاشته: هوم، تاریخچه/چارت‌سازمانی، نقشه پروژه‌ها، صفحه پروژه/تور مجازی، و ۴۰۴).

## ۱. معماری کلی

سه لایه: وردپرس (CMS + اکثر رندر صفحات)، لایه API روی PHP (namespace سفارشی `icd/v1` روی WP REST API)، و یک **کتابخانه React سه‌بعدی مشترک** که در چند قالب وردپرس mount می‌شود، نه یک اپ یک‌بارمصرف فقط برای هوم‌پیج. این تصمیم مهم است: اگر سه‌بعدی فقط برای هوم‌پیج ساخته شود، وقتی نوبت به نقشه پروژه‌ها یا چارت سازمانی می‌رسد باید از صفر ساخته شود. پیشنهاد: یک پکیج React مستقل (Vite build) با چند «صحنه» قابل‌انتخاب (`scene=hero|map|orgchart|tour|404`) که همه از یک سیستم متریال/نور/توکن رنگی مشترک (بخش ۵ سند سیستم دیزاین) استفاده می‌کنند.

## ۲. مدل‌های محتوایی (Custom Post Types در وردپرس)

| مدل | فیلدهای کلیدی | توضیح |
|---|---|---|
| `Project` | عنوان، گالری، مشخصات، لوکیشن (مختصات نقشه)، **وضعیت** (آتی/در حال ساخت/بهره‌برداری/تکمیل‌شده)، شرکت مالک (اگر Option B)، تور مجازی (فایل/لینک) | فیلد وضعیت باید طبق سوال باز ۱ در sitemap تصمیم‌گیری شود: enum تک‌مقداری یا آرایه تگ. **پیشنهاد فنی: از ابتدا به‌صورت تگ (چندمقداری) پیاده‌سازی شود** حتی اگر فعلاً تک‌مقداری استفاده می‌شود — مهاجرت از enum به tags بعد از پر شدن داده گران است، برعکسش ارزان |
| `Company` | نام، درصد مالکیت، مدیریت، لیست پروژه‌ها | فقط اگر Option B تایید شود (پیشنهاد خود sitemap). اگر Option A انتخاب شود، این مدل حذف و `Project` به‌جایش استفاده می‌شود، اما پیشنهاد می‌شود حتی در Option A یک فیلد nullable `ownerCompany` روی Project نگه داشته شود |
| `BoardMember` | نام، سمت، بیوگرافی، عکس | حدود ۱۰ رکورد |

| `Unit` | پروژه مرتبط، متراژ، طبقه، قیمت، وضعیت (موجود/رزرو/فروخته‌شده)، پلن طبقه | زیرمجموعه `/sales/*` |
| `JobPosting` | عنوان، شرح شغل، فرم درخواست | برای `/careers` |

| `Document` (کاربر) | نوع مدرک، فایل، وضعیت تایید | `/account/documents` — نیازمند ملاحظات امنیتی بخش ۸ |

## ۳. لایه API (PHP)

گسترش WP REST API با namespace `icd/v1`. جدول endpointهای کلیدی:

| Endpoint | Method | کاربرد |
|---|---|---|
| `/wp-json/icd/v1/projects?status=&company=&lang=` | GET | فید ۴ ایندکس پروژه + نقشه سه‌بعدی |
| `/wp-json/icd/v1/companies` , `/companies/{slug}` | GET | فقط Option B |
| `/wp-json/icd/v1/units?project=&status=&price_min=&price_max=` | GET | فیلتر واحدهای فروش |
| `/wp-json/icd/v1/ir/symbol` | GET | داده لحظه‌ای نماد بورس (بخش ۶) |
| `/wp-json/icd/v1/ir/disclosures?year=` | GET | آرشیو اسناد مالی + تقویم مجامع |
| `/wp-json/icd/v1/media/{type}?limit=` | GET | اخبار/روایت/گزارش |
| `/wp-json/icd/v1/search?q=&type=` | GET | جستجوی سراسری (بخش ۷) |
| `/wp-json/icd/v1/account/favorites` | GET/POST/DELETE | نیازمند احراز هویت |
| `/wp-json/icd/v1/tickets` | GET/POST | تیکت پشتیبانی، پیام مدیرعامل، شکایت — همه از این یک endpoint با فیلد `type` |
| `/wp-json/icd/v1/contact` | POST | فرم تماس/مشاوره → CRM |

همه endpointهای عمومی پارامتر `lang` می‌گیرند (بخش ۵ همین سند)؛ endpointهای `account/*` نیاز به `X-WP-Nonce` یا JWT دارند.

## ۴. احراز هویت و حساب کاربری (`/auth`, `/account/*`)

این بخش «APP» است، نه صفحه استاتیک — یعنی وردپرس کلاسیک به‌تنهایی برایش مناسب نیست. دو گزینه:

- **گزینه سبک (پیشنهادی برای v1):** پلاگین عضویت (مثل خود سیستم کاربری وردپرس + یک پلاگین OTP فارسی، یا پلاگینی مثل Ultimate Member سفارشی‌سازی‌شده) با قالب‌های اختصاصی هم‌راستا با سیستم دیزاین. هزینه کمتر، محدودیت بیشتر در UX.
- **گزینه کامل:** یک SPA کوچک React (مثل ماژول سه‌بعدی هوم‌پیج) فقط برای مسیر `/account/*`، که به همان API وصل می‌شود. UX بهتر برای favorites/orders/tickets که ماهیتاً تعاملی‌اند.

پیشنهاد: با گزینه سبک شروع شود (چون در P2 قرار دارد طبق اولویت‌بندی خود sitemap)، و اگر نیاز UX پیچیده‌تر شد در فاز بعد به SPA مهاجرت شود — چون همان API از الان طراحی می‌شود، مهاجرت فقط تغییر لایه نمایش است.

احراز هویت: OTP پیامکی برای کاربر عادی (استاندارد سایت‌های ایرانی)، به‌علاوه گزینه رمز عبور برای کاربرانی که ترجیح می‌دهند.

## ۵. دوزبانگی (fa-IR اصلی / en ثانویه)

تصمیم باز sitemap (سوال ۳: ترجمه کامل یا سایت انگلیسی کوچک ~۱۰ صفحه) مستقیم روی معماری اثر می‌گذارد: اگر ترجمه کامل باشد، از ابتدا **WPML یا Polylang** با تمام پست‌تایپ‌ها فعال شود و هر endpoint API پارامتر `lang` را پاس بدهد (همان‌طور که در بخش ۳ آمده). اگر سایت انگلیسی کوچک کافی باشد، صفحات EN می‌توانند صفحات استاتیک جدا باشند بدون دوگانه‌سازی کامل content model — هزینه و زمان توسعه به‌طور محسوس کمتر می‌شود. **پیشنهاد: این تصمیم قبل از شروع مدل‌سازی محتوا (فاز P0) گرفته شود**، چون افزودن چندزبانگی کامل بعد از ساخت اولیه یعنی migrate کردن تمام پست‌تایپ‌ها.

## ۶. یکپارچگی دیده‌بان ثاخت (Investor Relations)

سوال باز sitemap (۴): داده نماد بورس از TSETMC چطور تامین شود؟ سه گزینه با سطح ریسک متفاوت:

- **ویجت رسمی embed شده از TSETMC/کدال:** کمترین کار فنی، اما کنترل کمتر روی ظاهر (باید با سیستم دیزاین هماهنگ شود یا در iframe جدا نگه داشته شود).
- **Polling سمت سرور (cron وردپرس هر چند دقیقه یک‌بار از API عمومی TSETMC می‌خواند، cache می‌کند، از `icd/v1/ir/symbol` سرو می‌شود):** کنترل کامل روی طراحی ویجت، بار کمتر روی TSETMC، اما نیاز به نگهداری.
- **کش دستی/بروزرسانی توسط تیم:** فقط اگر داده لحظه‌ای الزام قانونی/رقابتی نداشته باشد؛ ریسک قدیمی‌شدن داده در سایت مالی-حساس بالاست، توصیه نمی‌شود.

**پیشنهاد فنی: گزینه دوم (polling سمت سرور با cache).** هم‌راستا با سیستم دیزاین است و وابستگی لحظه‌ای به دسترس‌بودن TSETMC ندارد. اسناد مالی (PDF) از طریق کتابخانه رسانه وردپرس با تاکسونومی سال/نوع مدیریت شوند و لینک به کدال به‌عنوان منبع رسمی حفظ شود، نه جایگزین آن.

## ۷. جستجوی سراسری

با ۸+ نوع محتوا (پروژه، شرکت، خبر، روایت، گزارش، عضو هیئت‌مدیره...)، جستجوی پیش‌فرض وردپرس (فقط عنوان/متن پست) کافی نیست. پیشنهاد: پلاگین جستجوی وردپرس با ایندکس بهتر (مثل SearchWP) یا در صورت رشد حجم محتوا، یک سرویس ایندکس جدا (Meilisearch/Typesense) پشت همان endpoint `icd/v1/search`. برای v1 با حجم محتوای مشخص‌شده در sitemap (~۸۶–۹۵ URL)، پلاگین وردپرسی کفایت می‌کند؛ سرویس جدا را فقط اگر حجم محتوا چند برابر شود توصیه می‌کنیم.

## ۸. امنیت و انطباق

- **مدارک هویتی (`/account/documents`, سوال باز ۷ sitemap):** اگر مدرک هویتی واقعی آپلود می‌شود، فایل باید رمزنگاری‌شده ذخیره شود، دسترسی محدود به نقش‌های مشخص باشد، و سیاست نگهداری/حذف داده مشخص شود — این یک تصمیم حقوقی است، نه فقط فنی؛ باید قبل از توسعه این بخش با تیم حقوقی/رعایت (compliance) هماهنگ شود.
- ارتباط React ↔ PHP از طریق HTTPS + `X-WP-Nonce` برای عملیات نوشتنی؛ CORS محدود به دامنه واقعی سایت.
- تیکت‌های پیام مستقیم مدیرعامل (SLA ۷۲ ساعته، سوال باز ۵ sitemap): برای v1، همان مدل `Ticket` با فیلد `type=ceo-message` و یک ایمیل/نوتیف داخلی کافی است؛ یک بک‌اند helpdesk کامل فقط اگر حجم پیام‌ها زیاد شود توجیه دارد.

## ۹. عملکرد، سئو و Fallback

صحنه‌های سه‌بعدی (هوم، نقشه پروژه‌ها، چارت سازمانی، تور مجازی) با glTF + فشرده‌سازی Draco بارگذاری شوند. هر صفحه‌ای که صحنه سه‌بعدی دارد باید یک fallback غیرسه‌بعدی (تصویر/HTML) داشته باشد — به‌ویژه صفحه ۴۰۰/۵۰۰ که sitemap صریحاً نوشته «باید بدون WebGL هم رندر شود». محتوای اصلی هر صفحه سه‌بعدی (تیتر، توضیح، لینک‌ها) به‌صورت HTML معمولی هم رندر شود تا هم سئو و هم صفحه‌خوان (screen reader) پوشش داده شود.
