# Architecture Decision Log

## ADR-001: Migrate frontend from React/Vite to Nuxt 4 + WPNuxt
- **Status:** accepted
- **Date:** 2026-09-23
- **Context:** The project's original architecture (docs/technical-requirements-icd3d.md) specified WordPress + a custom PHP REST API layer (`icd/v1`) + a shared React/Vite 3D module. The project owner explicitly approved replacing this with `wpnuxt-ui-boilerplate-full`'s architecture: Nuxt 4 + Vue 3 + TypeScript + WPGraphQL via `@wpnuxt/core`/`@wpnuxt/blocks`, as a full in-place replacement.
- **Decision:** The frontend is rebuilt on Nuxt 4 + WPNuxt, following `wpnuxt-ui-boilerplate-full`'s required project structure (`app/components/{ui,sections,wordpress}`, `composables/`, `extend/queries/`, layer boundary `pages -> sections -> ui -> composables -> WPNuxt -> WordPress`). `docs/technical-requirements-icd3d.md`'s custom PHP `icd/v1` API layer is superseded — WordPress content is now reached through WPGraphQL, not a bespoke REST namespace.
- **Consequences:** The design system (docs/design-system-icd3d.md), route table (docs/01-sitemap.md), and RTL rules are unchanged and still authoritative — only the delivery framework and CMS integration method changed. `docs/technical-requirements-icd3d.md` §3 (PHP API endpoint table) no longer describes the real integration path; it should be read as historical/superseded rather than updated line-by-line, since the content models in §2 are still valid and should be implemented as WPGraphQL/WPNuxt queries + WordPress custom post types instead.
- **Alternatives:** Keep the React/Vite + PHP API architecture (rejected — explicitly superseded by owner instruction).

## ADR-002: WPNuxt modules load conditionally, only once a real backend exists
- **Status:** accepted
- **Date:** 2026-09-23
- **Context:** `@wpnuxt/core` hard-requires a reachable WPGraphQL endpoint to boot `nuxt dev`/`nuxt build` (not only to introspect types for codegen) — confirmed by testing against a placeholder URL, which fails the entire app rather than degrading gracefully. No WordPress/WPGraphQL backend exists yet for this project.
- **Decision:** `@wpnuxt/core` and `@wpnuxt/blocks` are only added to `nuxt.config.ts`'s `modules` array when `WPNUXT_WORDPRESS_URL` is set (see `nuxt.config.ts`). All pages currently render from local view-model data in `app/utils/*Data.ts` (ported from the project's own prior React implementation, not placeholder copy) rather than WPNuxt composables.
- **Consequences:** The frontend can be built, previewed, and reviewed today with zero WordPress backend. The moment staging WordPress + WPGraphQL is live, setting `WPNUXT_WORDPRESS_URL` (see `.env.example`) turns the modules back on with no other code change. Each page's data-fetching still needs to be rewired from the local view-model files to real WPNuxt composables/queries once the content models in docs/technical-requirements-icd3d.md §2 exist in WordPress — tracked in the Project Progress Checklist in this repo's `CLAUDE.md`.
- **Alternatives:** Stand up a throwaway/mock WPGraphQL server just to satisfy the module (rejected as unnecessary overhead before real content modeling decisions — sitemap §13 — are made).

## ADR-003: 3D hero scene (HeroScene/CloudSystem/TehranTower) not yet ported
- **Status:** accepted (tracked, not resolved)
- **Date:** 2026-09-23
- **Context:** The prior React implementation's Three.js hero scene components (`src/components/HeroScene.jsx`, `CloudSystem.jsx`, `TehranTower.jsx`) were deleted along with the old `src/` tree during the migration and were never committed to git, so they could not be recovered (unlike `ClusterHub`, `ProjectsMapExplorer`, and `ProjectDetail`, which the project owner recovered from editor history and were ported faithfully).
- **Decision:** The homepage hero (block 0) currently renders the non-3D fallback state only (dark gradient + title + CTA), which already satisfies docs/technical-requirements-icd3d.md §9's requirement that every 3D page have a non-WebGL fallback. `app/components/sections/HeroSection.vue` has a code comment marking where a client-only 3D scene mounts.
- **Consequences:** The homepage is functionally complete but visually simpler than before until the 3D hero is rebuilt. Rebuilding it is a discrete, trackable task (3D scene work does not block any other page).
- **Alternatives:** Reconstruct the scene from memory of the deleted files (rejected — would not be the owner's real prior work, and risks silently fabricating implementation details).

## ADR-004: The About cluster is one page, not nine
- **Status:** accepted
- **Date:** 2026-10-11
- **Context:** docs/01-sitemap.md v1.1 §4 specified nine routes under `/about` (hub, history, ceo, board, board/[slug], vision, org-chart, honors, csr). In review the project owner judged the implemented result too cluttered and text-heavy, and asked for a merged, image-led, minimal treatment — About first, then the same pattern across the rest of the site. The About content is also one continuous narrative (founded ۱۳۳۰ as پارس سازه → ۱۳۶۴ → TSE listing → today), which nine separate pages actively fragment.
- **Decision:** `/about` is a single long-scroll page. The eight sub-routes are **deleted, not redirected**, and their content becomes anchored sections on `/about` in the order fixed in sitemap §4.1. The About mega-menu still lists seven destinations, but they are in-page anchors (`/about#history`), not routes. Two v1.1 pages are dropped as separate concerns rather than merged: the standalone interactive org chart (folded into `#committees`) and the CSR/ESG page (folded into `#vision`). Individual board-member profile pages (`/about/board/[slug]`) are removed entirely — each member is one flat card carrying name, position, education, company represented and a two-line bio.
- **Consequences:** Eight deep links, eight sets of page metadata and eight independently indexable pages are gone; `/about` carries that SEO weight alone. Anchor links remain shareable, and each section keeps its own heading level, which partly mitigates it. `app/utils/routes.ts` now exposes About anchors rather than routes, and those anchor ids **must stay in sync with `app/components/sections/AboutOverview.vue`** — there is no test enforcing this, so a renamed section id silently breaks the mega-menu. If the live site currently serves `/about/*` URLs, they need 301 redirects to the matching anchor (sitemap §13 open question 10). The CEO direct-message channel lost its dedicated page and its published 72-hour SLA has no entry point in the new structure — tracked as sitemap §13 open question 5, not resolved here.
- **Alternatives:** Keep the nine routes and simply shorten each page (rejected — would preserve deep links and per-page SEO, but nine short pages cannot tell one continuous story, which was the owner's actual goal). Merge but add 301 redirects immediately (deferred rather than rejected — depends on whether the old URLs are live, which is unconfirmed).

## ADR-005: Media consolidates to one categorised blog; performance reports move to IR
- **Status:** accepted
- **Date:** 2026-10-11
- **Context:** sitemap v1.1 §8 split Media into three branded indexes plus three detail templates (نبض ثاخت، روایت ثاخت، کارنامه ثاخت), specifically so the cluster would occupy one header slot while preserving three client-requested sub-brands. The owner then asked for the blog to be consolidated with categories, and separately asked for company and committee performance reports to be merged into the stock-exchange page. These two instructions interact: «کارنامه ثاخت» was simultaneously a Media sub-brand and the home of the performance reports.
- **Decision:** `/media` becomes a single `INDEX` with a category field on the `Article` model, filtered by query string (`/media?category=news`), and `/media/[slug]` becomes the single detail template for every post type, rendering an audio player when the post is a podcast. Categories at launch: `news`، `stories`، `podcast`، `analysis` (`tenders` added by ADR-009). Formal company and committee performance reports move under Investor Relations, where each report must be **both readable in-page and downloadable**. *(Amended by ADR-009: the destination is `/ir/financials`, not the separate `/ir/reports` routes originally specified here.)* The «کارنامه ثاخت» Media sub-brand is retired. What remains in `/media` is editorial; what moved to `/ir` is formal disclosure.
- **Consequences:** Six Media routes become three. Categories are now a content value rather than a route, so adding one costs a database entry — the same reasoning as the project status model (sitemap §5.1). Reports gain the audience that actually reads them and sit alongside the financial statements, but `/ir` grows and its exemption from the image-led style (ADR-008) becomes load-bearing. The requirement that reports be readable **and** downloadable is a real implementation cost: a PDF-only archive would have been cheaper, but is unsearchable, unreadable on a phone and invisible to crawlers, which is unacceptable in the one cluster where transparency is a regulatory obligation. Old `/media/news/*`, `/media/stories/*` and `/media/reports/*` URLs need redirects. The word «کارنامه» still carries three distinct meanings across the site (`/about#track-record`، `/projects/completed`، `/ir/reports`) — retiring the Media sub-brand reduced four to three but did not resolve it; final Persian copy must disambiguate (sitemap §13 open question 4).
- **Alternatives:** Keep the three sub-brands and add categories inside each (rejected by the owner — preserves brand names but not the consolidation). Keep reports in Media and mirror them into IR (rejected — duplicates a destination, and a regulated document with two homes will drift).

## ADR-006: `/careers` absorbs the HR topics and reduces to a two-field form
- **Status:** accepted
- **Date:** 2026-10-11
- **Context:** sitemap v1.1 listed `/careers` as a single `INDEX` + `FORM` page with no HR content specified. The owner asked for a brief intro plus a simple resume form requiring only a name and contact number, and separately specified that the HR section carry exactly three topics: benefits and employee welfare, FAQ, and learning and training — "no other items are needed."
- **Decision:** One page at `/careers`, in this order: brief intro over a photograph; the resume form (`#resume`); benefits and welfare (`#benefits`); learning and training (`#learning`); HR FAQ (`#faq`). No separate `/hr` route — the HR content is the reason someone scrolls this page, not a destination of its own. The form collects a name, a contact number and the attached file. Nothing else: no cover letter, no account, no multi-step wizard.
- **Consequences:** Route count stays flat while the page gains the employer-brand content. The minimal form maximises completion, but a name and a phone number cannot be deduplicated reliably, so the backend needs a submission timestamp and a hash of the attached file to detect repeat submissions — otherwise one applicant submitting three times is indistinguishable from three applicants. The page also now mixes a conversion goal (resume capture) with reference content (benefits, FAQ), so the form must stay above the reference sections rather than being pushed below them as the HR content grows.
- **Alternatives:** Two separate pages, `/careers` and `/hr` (rejected — adds a route and a footer slot for content nobody seeks independently). HR as a section inside `/about` (rejected — makes an already-long page longer and buries recruitment under corporate narrative).

## ADR-007: `/tenders` is a new top-level, footer-only route
- **Status:** ⚠️ **SUPERSEDED by ADR-009** (2026-10-11, same day). Kept for the record; do not implement.
- **Date:** 2026-10-11
- **Context:** The owner asked for registration rules and required-documents information to be moved to a tenders and auctions page. No such page existed in sitemap v1.1, in `app/utils/routes.ts`, or in `app/pages` — only a `tender` icon already present in `LeadForm.vue` hinted that one had been anticipated. The header budget is fixed at five content items plus one CTA (sitemap §10), so a sixth header slot was not available.
- **Decision:** A new top-level route `/tenders` (مناقصات و مزایدات) carrying the list of open tenders and auctions, the registration procedure, and the required-documents list. It is linked from footer column 4 and from search, **not** from the header. It requires a new `Tender` content model with title, type (مناقصه / مزایده), publication date, deadline, status and documents.
- **Consequences:** The site gains its 11th content model while the total route count still falls (sitemap §1) — the consolidation elsewhere paid for this. Status must be **derived from the deadline date, not a manually set flag**: an expired tender displayed as open is a procurement problem, not a display bug. The audience is suppliers and contractors who arrive by search or direct link, which makes footer-only placement correct but also makes this page's SEO and its direct-link stability matter more than its navigation. It sits in build wave P2 because it needs the model and a document pipeline — but if the client has a live tender to publish before launch it moves to P0, since an open tender with no page is a commercial loss.
- **Alternatives:** `/ir/tenders` (rejected — groups it with shareholder disclosure, but the audience is suppliers, not investors). A section inside `/about` (rejected — buries a page that suppliers need to find fast).

## ADR-008: Image-led minimal house style, with Investor Relations exempt
- **Status:** accepted
- **Date:** 2026-10-11
- **Context:** The owner's review of the implemented site was that it is too cluttered and too text-heavy, and asked for every page to become more concise and minimalist with greater emphasis on images. Applied uniformly, this would also reach `/ir`, whose audience is shareholders, analysts and regulators looking for a specific document under time pressure.
- **Decision:** An image-led, minimal house style applies site-wide (sitemap §14): image over sentence where both say the same thing; minimum 120px between sections; flat surfaces with no nested cards, shadows, gradients or decorative icons; one accent colour; editorial rather than brochure register. An enforceable text budget accompanies it — hero 8 words, section heading 4, section body 25, image caption 6, timeline entry 6 — targeting roughly a 70% reduction in text volume. **`/ir` and everything under it is explicitly exempt.** There, minimal means fast, plain and dense: a searchable, instantly loading document list with timestamps and no hero imagery.
- **Consequences:** The text budget gives reviewers something checkable and gives the content team a brief they can write to, rather than "concise" drifting back to paragraphs by the third review. The IR exemption is recorded explicitly so a later design pass does not "fix" the inconsistency. The style depends entirely on photography that may not exist: usable images per project, archival material for پارس سازه and the pre-۱۳۵۰ years the `#history` timeline opens with, and brand-film footage. **Asset availability, not layout, is now the critical-path risk** (sitemap §13 open question 3). If the archival photography does not exist, the black-and-white historical timeline needs a different visual device and this ADR should be revisited rather than worked around with stock imagery.
- **Alternatives:** Apply the style uniformly including IR (rejected — would produce a beautiful page that obstructs the only audience whose needs there are non-negotiable). Keep the style as informal review guidance without a text budget (rejected — unmeasurable, and the clutter being fixed here is what that approach produced the first time).

## ADR-009: Tenders are informational; the IR documents page is one route
- **Status:** accepted — **supersedes ADR-007**, amends ADR-005
- **Date:** 2026-10-11
- **Context:** ADR-007 created a standalone `/tenders` page on the assumption that tenders and auctions were a procurement destination, and specified a `Tender` content model with status derived from a deadline date. The project owner then clarified that this section is **purely informational**: the company publishes notices and updates about tenders and auctions, it does not run a bidding or registration process on the site. The owner also described a single page holding financial statements, official board reports, the legal requirements for document registration, and the downloadable materials — and noted that the tender PDFs were previously hosted in that same section. ADR-005 had meanwhile split official documents across `/ir/financials` (statements) and new `/ir/reports` routes (committee performance reports), which does not match that description.
- **Decision:** Two changes. **(1) `/tenders` is deleted.** Tender and auction content appears in exactly two places: as a `tenders` category in the Media blog (`/media?category=tenders`), and as document records on the IR documents page. There is no `Tender` content model — a notice is an `Article` with `category: 'tenders'`, and a tender document is a document record. There is no deadline-derived status logic and no footer navigation entry. **(2) `/ir/financials` and `/ir/reports` merge into one route, `/ir/financials`**, relabelled «اسناد و گزارش‌ها», carrying financial statements, board activity reports, committee performance reports, tender and auction notices, the legal requirements for document registration, the required-documents list, and every PDF download on the site. Detail view is `/ir/financials/[slug]`, readable as HTML with the PDF beside it.
- **Consequences:** Template count falls from 44 to 42 (Option B) and the content-model count returns from 12 to 11, since the `Tender` model is no longer needed. Content that is only ever read now sits where readers already are rather than on a destination of its own. `/ir/financials` becomes the single most load-bearing route on the site — every official document and every PDF is reached through it — so it moves early in build wave P1 and its filtering by document group and year is not optional. The route slug still reads `financials` while the page now carries tenders and registration rules, which will read oddly to anyone working in the code; renaming it to `/ir/documents` is cheap now and expensive after launch (sitemap §13 question 12). Two migration items appear: the tender PDFs' current URLs need redirects to `/ir/financials` and the files need moving (§13 question 11), and dated notices must display a publication date so an old notice is not read as current — the one risk the deleted deadline logic was guarding against that still applies. **If tenders ever become transactional on the site, this decision reverses**: a real `Tender` model with deadline logic becomes necessary, and the informational treatment becomes actively unsafe rather than merely insufficient.
- **Alternatives:** Keep `/tenders` as a thin page that merely links to the blog category and the IR page (rejected — a page whose only content is links to the real content is the clutter this whole consolidation is removing). Keep `/ir/financials` and `/ir/reports` separate and put tender content only on the former (rejected — the owner describes one page, and a regulated document with two plausible homes will drift; the merge is the whole point). Rename to `/ir/documents` as part of this ADR (deferred, not rejected — raised as an open question so the owner decides rather than inheriting a slug that no longer matches its page).

## ADR-013: The Stitch designs are the implementation source; Tailwind is adopted as a bridge
- **Status:** accepted
- **Date:** 2026-10-11
- **Context:** Eighteen page designs were generated in Google Stitch and placed in `stitch_project_detail_page_template/`. A review of them found three systemic faults — every page loaded fonts from `fonts.googleapis.com` (unreachable from Iran), sixteen of eighteen used `border-radius: 0` (a decision `docs/design-system-icd3d.md` §4.1 had explicitly **revoked** after feedback that it read as cold and unapproachable), and three different typefaces appeared across the set including Work Sans, which has no Persian glyphs. All three traced to the Stitch `DESIGN.md`, which carried a full Material token set (~50 colours including an orange tertiary) and declared `fontFamily: Work Sans` on every typography token. An alternative set of screens was then built directly on a design canvas with correct tokens. The project owner compared both and judged the **Stitch designs superior**, and asked for the project to be implemented from them and made runnable locally. The designs are authored in Tailwind utility classes; the Nuxt app had no Tailwind and styled its existing components from CSS custom properties in `app/assets/css/tokens.css`.
- **Decision:** **(1) The Stitch output is the implementation source of truth for page layout.** The canvas screens are retained only as reference for the routes Stitch never covered. **(2) Tailwind v4 is adopted**, loaded through `@tailwindcss/vite` in `nuxt.config.ts`. **(3) A bridge file, `app/assets/css/tailwind.css`, re-points every Material class name the approved markup uses onto this project's own tokens** — `primary-container` → `#005eb8`, `surface-container-lowest` → `#ffffff`, `surface-dim` → the border grey, and so on. `tertiary` and its family are deliberately left undefined so any surviving reference renders unstyled rather than quietly introducing an off-brand colour. **(4) The palette and corner geometry were corrected during the port; the type scale was not** — sizes stay as the designs were drawn, because changing them would reflow layouts the owner approved. **(5) Each design became a section component** under `app/components/sections/`, mounted by a thin page under `app/pages/`. Google Fonts links, the Tailwind CDN script, its inline config and all `<style>` blocks were stripped; Material Symbols icon spans were replaced with inline stroke SVG; `href`s were remapped onto the real route table (`/dideban` → `/ir`, `/media/reports` → `/ir/financials?group=committee-reports`, and the rest).
- **Consequences:** The project now carries **two styling systems**: the ported views use Tailwind utilities, while `IndexCardGrid`, `BoardMemberProfile`, `OrgChartView` and the `ui/` primitives still use `tokens.css` custom properties. This was accepted knowingly — Tailwind v4 emits every `@theme` entry as a real custom property on `:root`, so `var(--color-*)` keeps resolving for the older components and the two systems read the same values. **The ten palette values are now written in two files and must be kept in step**; `tokens.css` remains authoritative and `tailwind.css` says so at the top. Reconciling the two is a tracked follow-up, not a blocker. Every ported page sets `definePageMeta({ layout: false })` because the approved designs carry their own `<header>` and `<footer>`; until the shared `SiteHeader`/`SiteFooter` are reconciled with that chrome, rendering them inside `layouts/default.vue` would produce two of each. The ported markup is **static**: copy and data are inline, not yet wired to WPNuxt (ADR-002). Sixty Material icon ligatures had no SVG equivalent in the port and render as a dashed red-bordered placeholder carrying `data-icon-missing="<ligature>"` — visible in development and greppable, rather than silently showing the ligature text as words. The three faults that prompted this ADR cannot recur from the app side: fonts were already self-hosted in `public/fonts` with `@nuxt/fonts` deliberately removed, and the radius scale is enforced by the bridge.
- **Alternatives:** Convert the Tailwind classes to the existing `tokens.css` system (rejected by the owner — far slower, and visual drift would risk losing the fidelity that made these designs preferred). Keep the Stitch output byte-for-byte including the Material palette and sharp corners (rejected — would silently reverse design-system §4.1 and introduce an orange that is not in the brand). Regenerate all eighteen pages from a corrected `DESIGN.md` (attempted earlier; the corrected file is in place, but the owner preferred the existing output to another generation round).

## ADR-014: One shared chrome, a local icon registry, and placeholder assets until real ones arrive
- **Status:** accepted — **amends ADR-013** (its notes on `layout: false` and on `data-icon-missing` placeholders no longer apply)
- **Date:** 2026-10-11
- **Context:** After the ADR-013 port the site did not load locally, and the owner reported that the home page menu differed from the menu on every other page and that the designed pages rendered incorrectly. Investigation found six causes. (1) Every ported view carried its own copy of the header with the active tab hard-coded, and `layout: false` put the home page on the old `SiteHeader` — two different menus. (2) 157 image references pointed at Google-hosted URLs (`lh3.googleusercontent.com`), which do not load from Iran and are not ours to keep. (3) The bridge file `tailwind.css` on disk was a short first draft without the Material aliases, and it set `--spacing: 8px`, which doubles every Tailwind spacing utility (`p-4` became 32px instead of 16px). (4) The resets in `main.css` were unlayered, and in CSS cascade layers **unlayered rules beat every layered rule** — so `button { font: inherit }` and `a { color: inherit }` silently overrode Tailwind's utility classes. (5) 85 icons had no SVG in the port and showed as red dashed boxes; 70 more were inline SVG copy-pasted per page. (6) A handful of links pointed at routes the consolidation had removed (`/about/board`, `/about/ceo`, `/financial-reports`, `/sustainability`).
- **Decision:** **(1) One chrome.** `SiteHeader` and `SiteFooter` are lifted from the approved design and mounted once by `layouts/default.vue`; ported views are body-only and no page sets `layout: false`. The header nav is generated from `primaryNav` in `app/utils/routes.ts`, and the active item is derived from the current route. **(2) Placeholder assets.** Every image points at `public/img/placeholder.svg` (a neutral grey, aspect-free placeholder) until the owner supplies photography; swapping a real image in is a one-attribute change per use. **(3) Icon registry.** All icons go through `<AppIcon name="…" />` (`app/components/ui/AppIcon.vue`), backed by one map of 24×24 stroke paths in `app/utils/icons.ts`. It inherits `currentColor`, sizes at `1.25em`, is `aria-hidden` unless given a `label`, and the `IconName` type makes an unknown name a type error. No icon font, no CDN. **(4) Tailwind's default 4px spacing scale is kept**; named spacing lives in tokens (`space-xs`…`space-xl`, `gutter`, `margin`) instead of overriding `--spacing`. **(5) All resets in `main.css` live in `@layer base`**, so utilities always win. **(6) Removed routes map to their consolidated homes**: `/about/board*` → `/about#board`, `/about/ceo` → `/about#contact`, `/financial-reports` → `/ir/financials`, `/sustainability` → `/ir/financials?group=sustainability`. The home page follows the sitemap v1.5 block order with the CEO block removed and the subsidiaries block (خانواده ثاخت) placed before featured projects.
- **Consequences:** Verified on a clean production build: 30 of 30 routes return 200, an unknown route returns the designed 404, 0 dead internal links, 0 client-side errors, 0 horizontal overflow at 390px width. **Adding an icon now means adding one entry to `icons.ts`** — do not paste inline SVG into views. **Any new global CSS must go inside `@layer base` (or `components`)**, or it will override utilities without warning. The placeholder is deliberately plain, so a page that still shows it is visibly unfinished rather than looking done. Known content gaps carried forward from the designs, not introduced here: `/about` has no committees or vision section yet, `/ir/financials` lacks the annual financial tables and repeats one card block, shareholder table F has no data, and the home page IR widget is a text placeholder.
- **Alternatives:** Keep per-page chrome and only fix the active tab (rejected — two copies of a menu always drift). Material Symbols as a self-hosted font (rejected — about 300 KB for the ~100 glyphs used, and ligature text shows as words while the font loads). Keep the Google image URLs until real photography arrives (rejected — they do not load for the site's audience and are not licensed to us).

## ADR-015: Navigation opens the designed pages; one content catalog; illustrated placeholders
- **Status:** accepted — amends ADR-014 (placeholder style) and sitemap §6, §7, §10, §14 (v1.7)
- **Date:** 2026-10-12
- **Context:** Reviewing the site after ADR-014, the owner reported six problems: the «مشاوره و تماس سریع» button opened the old "contact the managers" page; project and subsidiary cards did not open the pages defined in the Stitch designs; the «فروش و پیش‌فروش» and «دیده‌بان ثاخت» menu items (and the pre-sale link) opened the old hub pages instead of the newly designed ones; the Media tabs did nothing; the grey placeholders made pages look broken; and images and frames still had sharp corners. A full audit found the causes. The header hard-coded `/contact` although `routes.ts` already named the consultation page as the CTA. The ported Stitch markup was static: cards were plain `<article>` elements with no link, and every detail page ignored its slug — any `/projects/…` URL showed the same tower. The designs' inline scripts (project and unit spec tabs, the careers upload/accordion/form) had been stripped in the port, so those controls threw errors when clicked. The Media post page used Font Awesome icons that never loaded. The home page's «خانواده ثاخت» block listed projects, not companies. Three retired Media routes were still live with the pre-consolidation templates, and the lead form still offered a CEO channel removed by ADR-010.
- **Decision:** **(1) The menu opens the designed pages**, matching the hrefs in the approved Stitch header: «فروش و پیش‌فروش» → `/sales` (the sales_available design, titled «فروش و پیش‌فروش», filterable by `?status=` and `?project=`); «دیده‌بان ثاخت» → `/ir/financials`; the CTA → `/sales/consultation`. `/sales/available`, `/sales/pre-sale` and `/ir` redirect (301) via `routeRules`; the retired `/media/news|stories|reports` routes redirect to their category or to the IR documents page. Every top-level item opens a dropdown of its sub-pages, mobile gets a drawer with the same tree, and the sales and IR clusters get a tab strip (`SubNav`). **(2) One content catalog** — `app/utils/catalog.ts` (companies, projects, sale units), `posts.ts` (media), `irDocuments.ts` and `financialTables.ts` (generated from the client's workbook).
